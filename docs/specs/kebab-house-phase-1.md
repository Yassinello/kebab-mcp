# Cahier des charges — Kebab House, phase 1 : une vitrine installable par des devs

> Source : brief vision « Kebab House » (13 novembre 2026). Phase 1 sur 4. Prérequis : phase 0 livrée.
> Contrainte dure : **aucune régression** pour une instance existante. Les jetons statiques (`Authorization: Bearer`, `?token=`) restent acceptés sans limite de durée.

## 1. Contexte

Trois constats de la recherche du 13 novembre 2026 cadrent cette phase :

- **OAuth est devenu la voie normale.** Claude n'accepte plus les en-têtes statiques que pour quelques organisations ; il propose sa propre identité publiée (CIMD) ou l'enregistrement dynamique (DCR). ChatGPT préfère aussi CIMD. Sans OAuth, l'installation dans Claude passe par un jeton collé dans l'URL.
- **Claude.ai ne transmet pas les `instructions` et ne gère pas l'elicitation.** L'onboarding et les validations ne peuvent compter ni sur l'un ni sur l'autre.
- **Kebab lit du contenu externe, le retient et peut écrire chez des tiers.** L'audit de novembre (§2.8) a reporté l'encadrement du contenu non fiable ; le garde-fou `confirm: true` des envois Unipile peut être passé par le modèle lui-même.

Le protocole MCP a aussi changé de génération (spec du 28 juillet 2026, sans session). `mcp-handler` 2.x exige le nouveau SDK `@modelcontextprotocol/server` 2.x ; Kebab est sur `mcp-handler` 1.1 / SDK 1.x.

## 2. Objectifs

1. Un modèle de confiance explicite : outils annotés, contenu externe signalé, provenance des notes, envois validés hors du modèle.
2. Un serveur d'autorisation OAuth 2.1 intégré, mono-propriétaire, compatible Claude, Claude Code, Cursor et ChatGPT.
3. Un onboarding conversationnel qui se lance par une phrase et un bouton « Ajouter à Claude ».
4. Une décision documentée, et si possible réalisée, sur la migration vers la génération 2026 du protocole.

Hors périmètre : passkey, gestion multi-utilisateur, Kebab Cloud, installeur sans Git.

## 4. Exigences — OAuth 2.1

## 7. Plan de livraison et vérification

1. Trois PR successives, chacune mergée avant la suivante : (a) modèle de confiance, (b) OAuth + onboarding, (c) protocole.
2. Avant chaque PR : typecheck, lint, `npm test`, build.
3. Vérification bout en bout locale : parcours OAuth complet avec un client simulé (DCR et CIMD), appels MCP avec jeton OAuth, parcours d'approbation d'un envoi (avec un fournisseur Unipile simulé), onboarding via `kebab_setup`.
4. Captures : page d'autorisation, page d'approbation, bouton « Ajouter à Claude ».
5. Après merge : vérification sur la production des points `/.well-known/*` et du 401 avec `WWW-Authenticate`.

## 8. Risques et arbitrages

- **CSP et redirections OAuth** : `form-action 'self'` peut bloquer une redirection 302 vers `claude.ai` après un POST dans certains navigateurs. La page intermédiaire de redirection (OAU-06) l'évite sans affaiblir la CSP.
- **Validation hors modèle (TRU-04)** : un clic de plus par envoi. C'est le but ; le mode `confirm` reste disponible pour qui l'assume.
- **Encadrement du contenu (TRU-02)** : change la sortie de nombreux outils ; l'opt-out existe pour un client qui l'interpréterait mal.
- **Migration de protocole** : le risque principal de la phase ; d'où la porte de décision PRO-01.
